# 多线程 06 · 并发程序的测试、调试与结课验收

> 前置：前五章、[工具链](../00-toolchain.md)
> 实验：[全部 labs](../../labs/README.md)
> 目标：区分测试能证明什么；定位数据竞争与挂起；建立正确性和性能两套证据。

## 1. 不同错误需要不同证据

| 问题 | 例子 | 合适的方法 |
|---|---|---|
| 数据竞争 | lab0 的普通共享 ++ | TSan、同步关系审查 |
| 生命周期错误 | 线程访问已销毁的引用 | ASan、所有权审查 |
| 业务竞态 | 余额检查与扣款分开 | 不变量断言、受控交错 |
| 死锁或无法退出 | 先 join 消费者再 close | 测试超时、所有线程栈 |
| 原子算法错误 | 原子 load + store 丢更新 | 串行规格对照、模型检查 |
| 性能倒退 | 细锁比粗锁更慢 | Release 构建与重复基准 |

“跑了十万次没错”是一条动态证据，不是覆盖所有调度和所有输入的证明。Sanitizer 未报告也不说明实现具备线性化、公平或异常安全等性质。

## 2. 三套独立构建

以下命令都从仓库根目录执行。先保证工具链同时提供编译器和支持所需 C++20 功能的标准库；编译器版本号本身不能保证 jthread 与 semaphore 可用。

```bash
# 正常功能测试与性能实验
cmake -S labs -B labs/build -DCMAKE_BUILD_TYPE=Release
cmake --build labs/build -j 4
ctest --test-dir labs/build --output-on-failure --timeout 120

# 数据竞争检测
cmake -S labs -B labs/build-tsan -DCMAKE_BUILD_TYPE=RelWithDebInfo -DLAB_SANITIZER=thread
cmake --build labs/build-tsan -j 4
ctest --test-dir labs/build-tsan --output-on-failure --timeout 180

# 内存错误与部分未定义行为检测
cmake -S labs -B labs/build-asan -DCMAKE_BUILD_TYPE=RelWithDebInfo -DLAB_SANITIZER=address
cmake --build labs/build-asan -j 4
ctest --test-dir labs/build-asan --output-on-failure --timeout 180
```

ASan 与 TSan 分开启用。Sanitizer 会改变时序并带来开销，不使用它们的耗时评价优化收益。平台、编译器运行库及沙箱可能限制工具运行；启动失败应记录为环境问题，不能写成“检测通过”。泄漏检测支持也随平台而异。

单独运行故意错误版本，**预期它报告错误**，不要把它并入“所有测试应成功”的套件：

```bash
./labs/build-tsan/lab0_race racy
```

先找报告中的当前访问和此前冲突访问，核对地址、调用栈、线程创建位置，再问二者之间缺了什么同步。先修第一个报告并复现，不要简单加 suppression 把课程要观察的缺陷隐藏掉。[LLVM：ThreadSanitizer 使用与限制](https://clang.llvm.org/docs/ThreadSanitizer.html)

## 3. happens-before 检测与 lockset 检测

向量时钟可以作为理解动态检测的模型。每个线程维护一个逻辑时间向量，线程内事件推进本地分量，同步时合并因果信息。如果两个冲突访问的时钟不能按分量比较出先后，就可能是未同步访问。实际 TSan 使用优化过的元数据与运行时机制，不是为每次访问永久保留一个完整向量。

Eraser 的 lockset 思路不同：对共享变量 x 维护候选保护锁集合 C(x)，每次访问时与当前持有的锁集合求交。如果候选为空，就提示缺少一致的加锁规则。实际算法还区分初始化、只读共享等状态，不能简化为“空集合必定是 bug”。[Eraser 原论文与作者页面](https://homes.cs.washington.edu/~tom/pubs/eraser.html)

比如先在一个线程初始化，启动另一个线程只读，未必有共同 mutex，却有合法的启动同步关系。反过来，一次未触发错误的运行也不代表下一次没有竞争。理解检测依据，才能分辨协议问题与工具建模限制。

## 4. 在编译阶段写出锁契约

Clang Thread Safety Analysis 可以用 `GUARDED_BY`、`REQUIRES` 等注解表达“字段受哪把锁保护”“调用函数之前必须持有什么权限”，再用 `-Wthread-safety` 检查。它是静态分析，不执行程序，也不增加运行时同步。[LLVM：Thread Safety Analysis](https://clang.llvm.org/docs/ThreadSafetyAnalysis.html)

这些名称通常是映射到 Clang 属性的宏，需要配套声明 capability 的锁包装类。不能只在普通 std::mutex 成员后面写一个未定义的 GUARDED_BY，就期待标准库自动提供全部注解。本课程 labs 尚未引入这种包装，适合先在一个小账户类上做独立练习。

静态锁契约、动态 TSan 与人工不变量证明互补：其中任何一个都不自动验证账本守恒或所有关闭路径。

## 5. 测试设计要刻意触发边界

现有测试是起点，扩展时可以按下表构造证据：

| 实验 | 已有主要检查 | 建议补强 |
|---|---|---|
| lab0 | 正确版本总数一致 | 局部归约；单独预期失败的 racy 检测 |
| lab1 | 各算法与串行结果比较 | 1×1、非整块尺寸、线程数大于行数 |
| lab2 | 并行最小 nonce 对照串行、余额和奖励守恒 | 两个提交者持有相同旧快照时只能一个提交 |
| lab3 | 重复插入失败、最终键集合与大小 | 小范围重复键冲突，与串行集合规格对照 |
| lab4 | 所有权、并发复制与析构 | 分配失败、未来弱引用扩展的回收路径 |
| lab5 | 返回值、任务异常、析构排空 | 部分线程创建失败与提交边界 |
| lab6 | 数量、最优航班、求和、关闭后拒绝写入 | 关闭唤醒、重复关闭、每个 ID 恰好一次 |

测试“恰好一次”时，为每条输入分配唯一 ID，收集消费者输出，join 后排序比较完整集合或核对每个 ID 的频次。只有总数或总和，可能漏掉“丢了一个又重复另一个”。不要让测试自身并发 push_back 到同一个无锁 vector；每线程独占收集区，最后归约。

需要安排关键交错时，用 barrier、latch、promise 或显式测试钩子建立阶段，例如让两个矿池都完成快照后再允许提交。睡眠只是概率性延迟，不能证明另一个线程已到达指定位置。启动屏障也不证明线程已经进入条件变量 wait；需要测试该精确阶段时，应加入受控观测点。

重复运行可扩大调度覆盖：

```bash
ctest --test-dir labs/build --repeat until-fail:20 --output-on-failure --timeout 120
```

超时只负责避免无限挂起。挂起时在调试器中抓取所有线程栈：GDB 用 `thread apply all bt`，LLDB 用 `thread backtrace all`。列出每个线程持有/等待的资源，画出等待关系，特别检查是否需要尚未执行的 close 或 notify。

## 6. 模型检查与小例子

压力测试探索实际运行到的路径；模型检查对小程序或有限模型系统地探索可能行为。CDSChecker 是针对 C11/C++11 原子内存模型的研究工具，不能假定它直接覆盖本仓库所有 C++20 库设施。[CDSChecker 官方仓库](https://github.com/computersforpeace/model-checker)

可以先把第 03 章的思想缩成两个原子变量、两个线程：

```text
初始 x=0, y=0
线程 A：x.store(1, relaxed); r1 = y.load(relaxed)
线程 B：y.store(1, relaxed); r2 = x.load(relaxed)
```

`r1 == 0 && r2 == 0` 在 relaxed 下允许，即使某台机器难以观测。如果四个操作都改为 seq_cst，统一全序就排除了该结果：要两次都读 0，就必须各自先于对方的 store，与各自线程的 store→load 顺序组成环。

探索时必须注明线程数、循环界限和所用内存模型。有限模型未找到反例，不能直接证明任意规模生产程序正确。

## 7. 性能报告与结课项目

性能测试固定输入、随机种子、编译模式与线程数；先校验结果，再计时。至少记录 5 次结果的中位数，写清 CPU、标准库、是否含启动成本以及后台负载。不要从旧环境的一次数据推断当前机器的排名。

结课项目：把 lab6 的航班处理整理成“有界输入队列 → 多消费者各自计算 → 主线程汇总”的流水线。可以复用现有组件；扩展代码由学习者完成，以下是验收规格：

1. 串行实现作为基准，生成带唯一 ID 的固定输入；并行与串行的最优结果一致，平局时按 ID 决定顺序。
2. 队列容量至少覆盖 1、小于消费者数、常规容量三种情况；覆盖零条输入、单条输入与大量输入。
3. 正常路径等待生产者、关闭队列、等待消费者、汇总；解释所有引用和组件的生命周期。
4. 失败路径捕获并传回异常，关闭队列以唤醒阻塞者，等待所有线程，再向主线程报告失败；明确失败时是否允许剩余数据被丢弃。
5. 验证每个 ID 恰好消费一次；另行测试关闭后拒绝写入及空队列退出，不依赖睡眠“碰运气”。
6. 提交 Release 功能结果、可用平台上的 TSan/ASan 记录和一页性能对照；未能运行的检查写明原因。

参考设计：生产者和消费者共享一个生命周期更长的队列；每个消费者只写自己的结果槽与异常槽；发生错误时调用幂等 close，生产者检查 push 的返回值退出。所有线程 join 后，主线程读取异常槽并决定抛出或汇总。任务失败需要提前让阻塞者退出，不能等主线程读取 future 时才尝试解救已经死锁的流水线。

## 自测与参考答案

- **TSan 不报告，是否说明没有死锁？** 不说明，它主要检测数据竞争，部分环境的锁顺序检查也不是完整活性证明。
- **ASan 通过能否证明引用跨线程安全？** 只能说明已运行路径未发现对应错误，仍须证明存活期和访问同步。
- **为什么压力测试与受控交错都要做？** 前者覆盖更多真实调度，后者可稳定重现某个关键窗口。
- **结课标准是什么？** 能为每份共享状态指出所有者、同步关系、不变量和结束协议，并用可复现测试支撑这些说明。
