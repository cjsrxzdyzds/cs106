## 1. 并发与并行分别解决什么问题

并发让多个任务在重叠的时间段内推进，单核也可以通过调度做到；并行让多个任务真正同时执行，需要可用的执行资源。后台下载与界面响应是并发问题，矩阵乘法分给多个核是并行问题。创建更多线程并不自动缩短运行时间：启动、调度、同步和访存都会付出成本。

同一进程的线程共享地址空间。每个线程有自己的调用栈，但“局部变量”并不等于“线程私有”：一旦把栈变量的引用传给其他线程，它也成为共享状态。审查一个 lambda 时，先看捕获列表，再问谁会读写这些对象、它们何时销毁。

## 2. `thread` 拥有的是线程句柄

`std::thread` 从 C++11 开始提供。构造后线程即可运行；只能移动，不能复制。`join()` 等待执行完成，并使句柄不再 joinable；`detach()` 则放弃等待权，线程继续执行。

⚠️ 一个仍然 joinable 的 `std::thread` 析构时会调用 `std::terminate()`，即使其线程函数已经返回。`joinable()` 表示句柄仍关联线程，不表示线程此刻还在运行。异常路径同样必须处理这一所有权。

C++20 的 `std::jthread` 适合本课程的局部任务：析构时若仍 joinable，会先请求停止，再等待完成。停止是协作式的，线程函数不检查停止请求就会继续运行；普通条件变量也不会因停止请求自动醒来。[标准草案：jthread 生命周期](https://eel.is/c++draft/thread.jthread.cons)

下面是可独立编译的 C++20 程序：

```cpp
#include <cassert>
#include <thread>

int main() {
    int result = 0;
    std::jthread worker([&result] { result = 42; });
    worker.join();
    assert(result == 42);
}
```

`result` 比 `worker` 更早构造，且在工作结束后才读取、销毁。引用捕获不会延长生命周期；若改成 `detach()` 并离开作用域，后台线程可能访问已经销毁的变量。传给线程构造函数的普通实参默认会被复制或移动，需要引用语义时用 `std::ref`，仍须自己保证生命周期。

线程入口中未捕获的异常也会终止程序，外层创建线程处的 `try/catch` 捕获不到它。需要返回异常时，使用第 04 章的 `future`，或在线程内部捕获后保存 `std::exception_ptr`。

## 3. 数据竞争为什么是未定义行为

在本课程的普通线程场景中，若两个线程对同一内存位置执行冲突访问，至少一个访问不是原子的，且两次访问没有 happens-before 顺序，就构成 data race。读写、写写都可能冲突；只读不冲突。对象生命周期的开始或结束也可能与访问冲突。[标准草案：数据竞争](https://eel.is/c++draft/intro.races)

在 lab0 中，两个线程执行普通 `++counter`，概念上可能发生：

| 步骤 | 线程 A | 线程 B |
|---|---|---|
| 1 | 读取 0 | |
| 2 | | 读取 0 |
| 3 | 写入 1 | |
| 4 | | 写入 1 |

这个表用于说明“读—改—写”不是不可分割的操作，**不是对错误程序所有行为的枚举**。C++ 数据竞争是 UB，不能保证结果仅仅偏小，也不能因某次结果正确就认为安全。`volatile` 不提供线程同步，增加休眠同样无效。

data race 与 race condition 不相同。例如每次查询余额和每次扣款都分别加锁，内存访问可以没有 data race，但两个调用者仍可能同时通过余额检查，随后重复花钱。这是第 02 章的逻辑竞态。

## 4. 用 happens-before 推理可见性

happens-before 是语言规定的先后关系，不是观察墙上时钟得出的顺序。本课程主要使用三种跨线程连接：启动线程、解锁后成功获取同一把锁、线程结束后 `join()` 返回。第 03 章再加入原子的 release/acquire。

以上例为例：

```text
主线程：result 初始化 ── 创建 worker ───────── join 返回 ── 读取 result
                              │                   ▲
工作线程：                    └── 写 result ── 结束┘
```

线程内部顺序与这些同步连接可以串起来。因此写入发生在最终读取之前，`result` 不需要是原子变量。但若主线程在 `join()` 之前同时读取它，就缺少这条连接。

lab0 的 `join()` 只能保证主线程在汇总时看到已完成的结果，不能倒过来修复工作线程之间已经发生的数据竞争。两个工作线程的 `++counter` 之间仍须互斥或原子操作。

**SC-DRF 的使用边界**：只使用合适的互斥同步和 `seq_cst` 原子来消除数据竞争时，可以按保持各线程内部顺序的交错执行理解程序。仅仅“没有 data race”还不足以把所有弱内存序程序理解成这种交错；`relaxed` 的边界见第 03 章。

## 5. 把共享写入从设计中移除

lab1 让所有线程只读 A、B，每个线程独占 C 的一段行。不同的普通元素可以并发修改，不需要整张矩阵一把锁。前提是计算期间不改变容器结构，不触发扩容，并且区间不重叠；不要把这一结论直接套用到按位压缩的 `vector<bool>`。

结束顺序同样属于算法。lab1 在内部作用域销毁所有 worker，再 `return C`。返回语句可能先移动 C，再析构同作用域的 worker；如果线程仍通过引用访问 C，就会出错。NRVO 是可选优化，不能作为正确性的条件。

lab2 则必须显式 `join()`：工作函数检查 `stop_token`，若依赖 jthread 析构，请求停止可能使尚未检查完的较小 nonce 被跳过。“找到任意解”和“找到最小解”要求不同的结束协议。

## 练习与参考思路

1. 在线程启动前写 `result = 7`，线程只读它，主线程之后不再修改，是否安全？**思路**：初始化经启动同步关系传给新线程；引用还必须存活到线程结束。
2. 两个工作线程各写数组的一个不同 `int` 元素，主线程 join 后求和，是否需要原子？**思路**：不需要；各自独占写，join 负责最终读取的顺序。
3. 为什么“全部 join 后总数仍错误”不能靠增加 join 修复？**思路**：join 连接工作线程与等待者，没有把两个增量操作互相排成顺序。
4. 比较 lab1、lab2 的结束方式。**验收**：能解释为什么 lab1 的工作函数忽略停止请求，而 lab2 不能在正常求解时提前请求停止。
