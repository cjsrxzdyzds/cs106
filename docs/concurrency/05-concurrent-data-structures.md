> 目标：定义操作契约；比较锁粒度；理解节点生命周期和快照提交。

## 1. 先定义“正确”的含义

线程安全容器不只要求“没有数据竞争”，还要说明操作对外呈现什么行为。对只支持 insert/contains 的集合，可以规定：相同键只有第一次插入成功；已完成插入的键随后必须可查；没有插入过的键不能凭空出现。

**线性化（linearizability）**要求每个操作看起来都在调用与返回之间某个瞬间生效，且保留不重叠操作的真实先后关系。这个瞬间称为线性化点。两个重叠操作可以先后任意排列，只要存在一个符合串行规格的排列。

例如 A 插入 7 已经返回，B 才开始 contains(7)，B 必须返回 true；若 B 的查询与 A 的插入重叠，则可能返回 false。不能用“多线程输出顺序不固定”解释任何错误结果。

还要区分安全性与活性：不丢键是安全性；操作最终能完成是活性。无数据竞争仍可能死锁、饥饿或无限重试。

## 2. 一把全局锁是基线

lab3 的 CoarseBST 在整个操作期间持有同一把 mutex。底层 SeqBST 不需要自行同步，因为所有外部入口都遵守这一协议。

成功插入可把新节点链接到树的时刻作为线性化点；查询可选择在锁内观察到目标或空链接的时刻。节点没有并发删除，析构前也必须先等所有使用者结束。

这一设计容易论证和测试。代价是查询也互斥，吞吐量受串行临界区限制。它仍可能胜过复杂方案：临界区短时，多次锁操作的成本比允许的额外并发收益更大。

RwBST 把插入改为独占锁、查询改为共享锁，允许查询之间重叠。但树操作很短、共享锁内部竞争激烈时，读写锁可能更慢。不要从“读多写少”直接跳到性能结论。

## 3. Hand-over-hand：拿稳下一个节点再放手

HohBST 每个节点有一把锁，根链接有单独的 root_m。沿路径移动时遵循：

```text
持有父链接所属锁 → 读取子节点 → 锁住子节点 → 释放父锁 → 继续向下
```

`root_` 由 root_m 保护；一个节点的 left/right 链接由该节点自己的 mutex 保护。读取一个链接之前，必须持有拥有这个链接的那把锁。局部变量 slot 指向某个 unique_ptr 成员，并不自行提供同步。

所有路径都向下加锁，没有反向取得祖先锁，因此在本实验的插入/查询模型下不会形成锁顺序环。操作最多同时持有两把锁，不同子树上的操作可以重叠，但所有访问仍先经过根部。

lab3 的 key 构造后不变，节点只插入不删除；这些限制是正确性论证的一部分。unique_ptr 清楚表达树的所有权，但不会自动保护其他线程手里的 Node*。

### `size()` 需要单独说明

HohBST 在持有父链接所属锁时链接新节点并增加原子计数，随后才释放这把锁。其他查询不能越过该锁观察尚未完成计数更新的新链接，因此分析成功插入时，可以把计数增加作为生效点。计数本身的并发读取不需要取得整棵树的锁。

但一次 size 调用并不会替后续遍历保留快照：两次调用之间可能继续插入，也不能因为大小非零就无保护地访问节点。当前测试在所有线程 join 后核对最终 size；若扩展删除或遍历接口，需要重新证明它们与计数更新的关系。

## 4. 为什么删除更难

查询者读取到 Node* 后，另一线程若删除节点，前者可能尝试锁一把已经被销毁的 mutex。把根或子指针变成 atomic 只能保护指针值访问，无法延长目标节点生命。

有两个孩子的 BST 删除还涉及后继查找与多处链接更新；粗暴加入反向锁顺序会破坏原来的无环证明。稳妥练习顺序是先给 CoarseBST 增加删除，再写清细粒度版本的锁集合、顺序和回收条件，最后实现。

无锁数据结构的内存回收常使用 hazard pointer 或 epoch 等专门协议。前者让访问者公布正在保护的对象并重新验证，回收者延迟释放受保护节点；后者等所有可能持有旧引用的参与者离开相应时期后再回收。两者都需要完整参与协议，不是加一个全局计数即可完成。本章只说明边界，不要求自行实现通用无锁 BST。

数据库课程中的 latch crabbing 与这里共享“向下拿锁再放父锁”的思想，但数据库 B+Tree 还要处理节点分裂、合并、页生命周期及事务隔离。lab3 不是这些完整机制的实现。

## 5. lab2 的 OCC：快照—计算—验证—提交

挖矿搜索耗时长，如果整个 mine 都持独占锁，查询与提交交易都会被阻塞。lab2 把计算分成三段：

| 阶段 | 锁 | 工作 |
|---|---|---|
| 快照 | 共享锁 | 复制 pending 及 epoch |
| 搜索 | 无账本锁 | 在私有快照上找 nonce |
| 提交 | 独占锁 | 核对 epoch、转账、删掉已结算前缀、奖励、递增 epoch |

版本检查与更新必须在同一次独占临界区中，否则两个矿池都可能验证通过并重复提交。失败返回 nullopt，调用方决定重试、退避还是放弃。

为什么追加 pending 不递增 epoch 仍可以？**因为这个实现只在尾部追加，成功 mine 只移除快照对应的前缀**。没有其他提交时，旧快照仍是当前列表的前缀，新交易可以留待下一轮结算。若以后允许取消、排序或修改已有交易，必须改变版本更新与验证规则，不能照搬当前判断。

假设 A、B 都取得 epoch=5。A 提交后变成 6，B 再持锁验证发现不一致而放弃，不会重复奖励。其成功提交的外部效果在独占锁保护下完成；正确性还依赖有效账户、有限正金额等输入前提。这个实验使用 toy hash、double 和简化事务，没有实现生产账本的签名、精确货币表示及异常回滚。

## 6. 确定性是算法目标，不是调度特征

lab2 将 nonce 按线程数取模分配。每个线程按递增顺序搜索自己的序列，发现合法值后用 CAS 更新 best；越过 best 的候选不可能改进答案，可以停止。

某个线程先找到 100，不能立即取消所有线程：其他线程可能尚未检查 20。只有所有仍可能改善 best 的较小候选都完成后，最终最小值才确定。这就是正常求解时必须显式 join 的原因。

原子 best 的旧值只会让线程多搜索一些，因为 best 单调下降；不会跳过更小的候选。前提是各线程完整覆盖合法搜索域、线程数大于零，并正确处理范围和整数边界。实验使用有限且较小的范围，不是无限 nonce 空间的实现。


1. 指出 CoarseBST 成功插入和失败插入各自可选的线性化点。**思路**：链接新节点；在持锁时发现重复键。
2. 若允许撤销 pending 中任意一条交易，原 OCC 验证还成立吗？**思路**：不成立；快照可能已不是前缀，需更新版本并验证或更换提交协议。
3. 给粗锁 BST 增加 erase。**验收**：覆盖空树、重复删除、根、叶子、单孩子、双孩子；与串行 set 对照；并发时保留整操作持锁。
4. 为三种树设计公平基准。**思路**：相同键序列与线程数，区分只读、读写混合和重复插入；测试计时范围相同，记录树高或输入顺序，报告多次测量。
