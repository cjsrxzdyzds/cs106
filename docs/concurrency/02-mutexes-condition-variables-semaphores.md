# 多线程 02 · 互斥量、条件变量与信号量

> 前置：[线程与内存模型](01-threads-and-memory-model.md)
> 实验：[lab6 队列](../../labs/lab6_queue/bounded_queue.h)、[lab2 账本](../../labs/lab2_mining/mining.cpp)
> 目标：围绕不变量划定临界区；设计等待谓词；完成可退出的生产者—消费者协议。

## 1. 锁保护的是一组必须一起成立的事实

账本的不变量是“余额扣除已预留支出后仍足够支付新交易”。读取余额、统计预留支出、检查金额、追加交易必须是一次不可分割的业务操作。如果分别给 getter 和 setter 加锁，两个线程仍可能基于同一笔余额通过检查。

lab2 的 `add_pending_trx()` 先在锁外解析字符串，再持独占锁完成检查与追加。解析只使用私有数据，可以移出临界区；检查依赖共享状态，不能移出去。这比“尽量少加锁”更具体：缩短临界区，但保留不变量的完整检查与更新。

| RAII 类型 | 用途 | 注意 |
|---|---|---|
| `lock_guard` | 整个作用域持有一把锁 | 简单、不可手动解锁 |
| `unique_lock` | 等待、提前解锁、转移锁所有权 | 条件变量需要它临时解锁 |
| `scoped_lock` | 一次取得多把互斥锁 | 使用避免死锁的获取方式 |
| `shared_lock` | 取得 `shared_mutex` 的共享权限 | 共享区间内不能修改受保护状态 |

锁对象必须有名字：临时对象在语句结束就析构。也不要返回指向受保护容器内部的裸引用，然后期望锁在函数返回后继续保护它；可以返回拷贝，或明确设计携带锁所有权的访问接口。

## 2. 死锁与固定加锁顺序

若 A 持有锁 1 等锁 2，B 持有锁 2 等锁 1，就形成环形等待。转账需要同时访问两个账户时，先处理同一账户的特殊情况，再用 `std::scoped_lock(a.m, b.m)` 同时取得两把锁，或让所有路径按同一稳定顺序获取锁。

⚠️ `scoped_lock` 不会修复所有死锁：在持锁时调用用户回调，回调可能重新获取同一把非递归锁；持锁等待一个需要该锁的线程结束，也会死锁。lab5 因此在取出任务之后释放队列锁，再调用任务。

`shared_mutex` 允许多个读者或一个写者。读多不等于一定更快，读写锁维护状态也有成本，标准也不保证某一种公平策略。从共享锁升级为独占锁时，不应直接再次锁同一个 mutex；释放共享锁后取得独占锁，必须重新检查原条件。

## 3. 条件变量等待的是状态

消费者真正需要的条件是“有元素可取，或者队列已关闭”。通知只是提醒重新检查条件，它不会储存一张可在未来消费的票。

lab6 的 `pop()` 核心如下（类内节选）：

```cpp
std::unique_lock lk(m_);
not_empty_.wait(lk, [&] { return closed_ || !q_.empty(); });
if (q_.empty()) return std::nullopt;
T value = std::move(q_.front());
q_.pop_front();
lk.unlock();
not_full_.notify_one();
return value;
```

带谓词的 wait 相当于 `while (!predicate()) wait(lk)`。等待会原子地释放锁并进入等待，被唤醒后重新取得锁，再检查谓词。这个结构同时处理虚假唤醒，以及“另一个消费者先拿走了元素”的正常竞争。[标准草案：condition_variable](https://eel.is/c++draft/thread.condition.condvar)

共享状态的修改和谓词检查使用同一把锁，才能避免“检查完为空、尚未等待时错过通知”的协议错误。通知通常可以在解锁后发送，因为状态已经在锁内更新；本实验要求队列始终存活，直到所有调用线程结束。不要把 `sleep_for()` 当作修补丢失唤醒的方法。

如果要实现超时，应使用固定截止时刻的 `wait_until` 或带谓词的定时等待；自己循环调用完整时长的 `wait_for` 可能因反复唤醒不断延长总等待时间。

## 4. 有界队列的状态与关闭协议

容量上限提供背压：消费者来不及处理时，生产者等待，而不是无上限地占用内存。lab6 有两个条件变量：`not_full_` 唤醒生产者，`not_empty_` 唤醒消费者。

| 状态 | `push` | `pop` |
|---|---|---|
| 开放且为空 | 插入并通知消费者 | 等待 |
| 开放且已满 | 等待 | 取出并通知生产者 |
| 关闭但非空 | 返回 false | 继续取出剩余元素 |
| 关闭且为空 | 返回 false | 返回 nullopt |

`close()` 在锁内置位，然后对两组等待者都 `notify_all()`。只通知消费者会让满队列上阻塞的生产者无法退出。重复关闭是幂等操作。

正确使用顺序是：启动消费者与生产者 → 等所有生产者完成 → close → 等所有消费者完成 → 销毁队列。不要先等待消费者，再关闭它们正在等待的空队列。

当前教学实现要求容量大于 0；传入 0 时，push 会等到关闭才失败。它也没有为任意会抛异常的 T 提供完整的恢复协议：例如移动失败后如何保留元素、如何通知其他等待者，需要额外设计。这些是推广为通用库时的工作，不能因为模板可实例化就忽略。

## 5. 信号量：先领取资源，再进入临界区

lab6 的 `SemaphoreQueue` 对应 CS:APP 的 sbuf。`slots` 表示空位许可，初始为容量；`items` 表示元素许可，初始为 0；mutex 保护环形数组及首尾下标。

```text
push：slots.acquire → 加锁写入 → 解锁 → items.release
pop ：items.acquire → 加锁取出 → 解锁 → slots.release
```

必须先等许可再持有 mutex。若消费者持有 mutex 等待 items，生产者就无法获得 mutex 写入元素，系统可能永久阻塞。信号量可以积累许可，条件变量通知没有这种计数语义。

在没有操作进行时，`slots + items = Capacity`；操作中可能已经领走许可但尚未发布对应许可，因此不能要求任意时刻这两个计数简单相加都等于容量。

这一实现没有 close，测试提前约定每个消费者取多少次。若数量未知，可以设计结束标记，但需要保证每个消费者最终收到一个，且不会和合法数据混淆。不能随意多 release 几个 items 来“关闭”：醒来的消费者可能读取根本不存在的元素。该实现还要求容量为正、T 可默认构造和赋值；若领取许可后移动抛异常，必须考虑归还许可，现有版本未实现这一恢复。

## 练习与参考思路

1. 为什么 `if (empty) wait()` 不够？**思路**：虚假唤醒和消费者竞争都会使醒来时队列仍为空，需要循环重查。
2. 为容量 0 增加参数检查。**验收**：构造立即抛 `invalid_argument`，不启动线程后才挂住。
3. 分别设计“空队列上阻塞的消费者”和“满队列上阻塞的生产者”遇到 close 的测试。**思路**：安排状态后调用 close，检查前者返回空、后者返回 false，并设置测试超时。
4. 为什么信号量不能代替保护环形缓冲区的 mutex？**思路**：许可只限制可推进的操作数量，多名生产者仍可能同时更新 rear。
